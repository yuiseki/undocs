# How UN documents are fetched now

Observed 2026-09-17. The scraper in `scripts/www.undocs.org/` was written
against a site that no longer exists in that form, and the machinery it needs
(manual session cookies, recursive redirect following, meta-refresh chasing)
turns out to be unnecessary against the current one.

## The site moved

`undocs.org` and `www.undocs.org` now answer 301 to `docs.un.org`:

    https://undocs.org/en/S/RES/2728(2024)
      -> 301 https://docs.un.org:443/en/S/RES/2728(2024)

`docs.un.org/{lang}/{symbol}` returns a viewer page, not a PDF. It is about
4 KB and holds two useful things: links to the same document in the other five
UN languages, and the PDF source.

    href="/ar/S/RES/2728(2024)"
    href="/es/S/RES/2728(2024)"
    href="/fr/S/RES/2728(2024)"
    href="/ru/S/RES/2728(2024)"
    href="/zh/S/RES/2728(2024)"
    src="https://documents.un.org/api/symbol/access?s=S/RES/2728(2024)&l=en&t=pdf"

## The access API

    https://documents.un.org/api/symbol/access?s={symbol}&l={lang}&t=pdf

It answers 302 with a `Location` giving the internal document path. The symbol
and the language go in as they are; the symbol keeps its slashes and its
parentheses.

No session cookie is needed. `docs.un.org` sets none at all; the API sets two
of its own (`ApplicationGatewayAffinity`), which are load-balancer stickiness
rather than authentication.

## The path comes back in the wrong case

This is the part that cost the most time. The API returns an uppercase path:

    location: /doc/UNDOC/GEN/N24/080/81/PDF/N2408081.PDF

The file is served at the lowercase one:

    https://documents.un.org/doc/undoc/gen/n24/080/81/pdf/n2408081.pdf

Following the uppercase path with curl fails in ways that look like something
else: a 301 to a 162-byte body, or a 200 carrying 1,303 bytes of HTML, which is
the Official Document System single-page app rather than an error. Lowercasing
the path and requesting it directly returns the PDF in about 1.2 seconds.

## Headers matter, and the API says which one

The API was returning `https://documents.un.org/error` for most requests until
the headers changed. It declares the reason itself:

    vary: Origin, Accept

Three things changed at once, so this is not a clean attribution: the
User-Agent went from Chrome 131 to Chrome 155, `Accept: application/pdf` was
added, and `Sec-Fetch-Site: same-site` was added. The `vary` header points at
`Accept`. Worth isolating before relying on it.

A request that works:

    curl -sI \
      -A 'Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/155.0.0.0 Safari/537.36' \
      -H 'Accept: application/pdf' \
      -H 'Sec-Fetch-Site: same-site' \
      -e 'https://docs.un.org/es/S/RES/2728(2024)' \
      'https://documents.un.org/api/symbol/access?s=S/RES/2728(2024)&l=es&t=pdf'

## Internal numbering is close to sequential but not derivable

For S/RES/2728 (2024):

| Language | Path stem | PDF bytes |
| --- | --- | --- |
| en | N2408081 | 159,846 |
| fr | N2408082 | 158,013 |
| ru | N2408084 | 502 from the server |
| es | N2408085 | 153,992 |

Consecutive, with gaps, and there is nothing in a document symbol that yields
the stem. The API has to be asked for each language. Nothing in the repository's
stored `metadata.json` records the real PDF URL either, only the `undocs.org`
entry point, so the existing corpus cannot be used to reverse the mapping.

`l=ja` returns the English PDF byte for byte. There is no Japanese, and an
unknown language code falls back to English rather than failing, which will
silently produce duplicates if the language list is not restricted to the six
official ones.

## 502s happen

Russian returned 502 with a 552-byte body on one attempt and a valid path on
another, minutes apart. Retries are needed, and a 502 has to be distinguished
from the 1,303-byte HTML app page, which arrives with status 200.

## What the current scraper does

Three things, none of them wrong at the time, all of them worth revisiting.

A year filter is hardcoded in `fetch.ts`:

```js
if (!resolutionId.includes("2020") && !resolutionId.includes("2021") &&
    !resolutionId.includes("2022") && !resolutionId.includes("2023")) {
  continue;
}
```

`data/www.undocs.org/all_docs_urls_uniq.txt` holds 41,942 URLs; `en/pdfs/`
holds 4,073 PDFs. The filter is the difference.

The language is hardcoded too: `"https://www.undocs.org/en/" + resolutionId`.

And `followRefresh` reads `res.headers.get("Set-Cookies")` where
`followRedirect` reads `"Set-Cookie"`. Cookies are dropped through the refresh
chain. Moot if the refresh chain goes away, but worth knowing why it behaved
oddly.

## What a rewrite needs

1. GET `https://documents.un.org/api/symbol/access?s={symbol}&l={lang}&t=pdf`
   with a current User-Agent, `Accept: application/pdf`,
   `Sec-Fetch-Site: same-site`, and `Referer: https://docs.un.org/{lang}/{symbol}`.
   Do not follow the redirect.
2. Take `Location`, lowercase it, and GET `https://documents.un.org{path}`.
3. Check the result is actually a PDF. A 200 of about 1,303 bytes is the app
   page, not a document.
4. Retry on 502 and on `/error`.
5. Restrict `l` to ar, en, es, fr, ru, zh. Anything else silently yields English.

At 41,942 symbols across six languages this is roughly 250,000 requests. At one
request every few seconds that is days, which is the right pace for someone
else's server.

## State of the data as of this writing

- 4,073 PDFs in `en/pdfs`, 1,243 under `A/` and 3,166 under `S/`, 1.3 GB
- 168 of them have `summary.txt` and `metadata.json`; the summaries are
  summaries, not full text, and no full text is stored
- `pdftotext` extracts 4,024 of 4,073 successfully: 2 failures, 47 too short to
  be text (likely scans), 69.5 MB of text, mean 17,265 bytes per document

## Why this is worth finishing

UN parliamentary documentation, which is what these are, is in the public
domain: documents issued under a UN document symbol and not offered for sale
are excluded from UN copyright. That is a less restrictive footing than CC BY
or CC BY-SA.

The six language versions are official translations of the same text, aligned
at document level by construction. A place named in all six is a naturally
occurring attestation of how that name is written in each, which gazetteers
assert but do not demonstrate.

And the register exists nowhere else: resolutions name places as their subject,
repeatedly, and cite earlier resolutions, so the same places recur across
documents in a citation graph.

## The symbol API is the bottleneck, not politeness

Measured 2026-09-18, three calls in a row:

    locate  S/RES/2728 (2024)    5.8 s
    locate  A/RES/70/1          17.5 s
    locate  S/RES/1325 (2000)   30.8 s
    fetch the PDF itself         1.0 s

Resolving a symbol to its internal path takes between six and thirty-one
seconds. Downloading the document it points at takes one. Whatever the API does
between `?s=` and the `Location` header, it is not fast and it is not
consistent.

This settles how to make a run finish sooner. `--delay` adds about 3.3 seconds
per job, which is noise beside a call that varies by twenty-five seconds, so
halving it changes almost nothing: going from two workers at 4.0 s to four at
2.0 s moved the rate from 573 to 706 documents an hour, 1.23x, when the
settings suggested four times.

Concurrency is the only lever that matters. Each job costs roughly twenty
seconds of mostly waiting, so the rate is about `workers / 20` per second.

Throttling was not what stopped the earlier run; a bug was. Over half an hour at
four workers the failure rate held at 0.29% to 0.31%, and every failure was a
malformed symbol such as `S/2022/X` redirecting to the error page, not a refusal
from the server.

## Ten workers is past the limit; four is not

**This section is wrong and is kept for the record. See the correction below.**

Measured 2026-09-18, half an hour at each setting.

| workers | delay | documents an hour | failure rate |
|---|---|---|---|
| 2 | 4.0 | 573 | 0.29% |
| 4 | 2.0 | 706 | 0.31% |
| 10 | 1.0 | 888 | 4.3% rising to 13.4% |

At ten workers the rate barely moved while the failures multiplied: 441
documents saved against 1,775 refusals in the same half hour, 2,362 of them
HTTP 503. The server does not queue the excess, it rejects it, so the extra
workers buy about a quarter more throughput and spend it several times over.

Four workers is the setting to use. The earlier conclusion that concurrency is
the only lever still holds; it just has a ceiling well under ten.

## A refusal was being written down twice, once as an absence

Found 2026-09-18. `locate()` leaves `path` unset both when it answers "no such
document" and when it raises, and the worker inferred absence from `path is
None`. So every exhausted retry wrote an `error` record and then fell through
and wrote a `missing` one for the same document. All 2,952 failed symbols had
both, and 4,567 of 4,579 error records sat immediately beside their twin.

That defeated the resume rule entirely. A `missing` is trusted as final, so
those documents would never have been tried again.

Absence is now something `locate()` states, carried in its own flag, and never
deduced from an unset path. The manifest was repaired by dropping 2,581
`missing` records that shared a key with an error and had no later `saved`.

This is the third form of the same mistake in this scraper: a request that did
not succeed being filed as an answer. The first conflated a 429 with absence,
the second let the resulting exception end the run silently, and this one wrote
the absence anyway.

## Correcting the worker measurements: there were three fetches, not one

Found 2026-09-18 during a scheduled check. Two fetches from earlier in the day
were still running, reparented to init, five and a half hours after they were
supposedly stopped.

The stop had killed the wrong process. `nohup python3 ... > log 2>&1 &` makes
bash fork a subshell to set up the redirection, so `$!` is the subshell and
python is its child. Killing the recorded pid killed the wrapper, `kill -0`
then reported it gone, and that was read as the fetch having stopped.

So the table above measures the wrong thing:

| the run labelled | workers actually against the API |
|---|---|
| 2 workers | 2 |
| 4 workers | 4 |
| 10 workers | 24, being 4 + 10 + 10 |

The four-worker figure of 0.31% was taken between 07:22 and 07:52, before the
second fetch started at 07:54, so it stands. The 13.4% attributed to ten workers
was measured against twenty-four and says nothing about ten. Where the ceiling
actually is remains unknown.

The lesson is not about workers. A kill that returns success is not a process
that stopped, and the pid to check is the one the kernel gave python, not the
one the shell handed back. `fetch.py` now takes a lock, so a launcher that
records the wrong pid can no longer double the load against the API.

## The error page means the document does not exist

Established 2026-09-18. A 302 to `https://documents.un.org/error` had been
classified as a refusal, on the reasoning that only a plain 200 states absence.
That was wrong.

Eight symbols the fetch had filed as refusals were probed three times each while
the server was answering a known-good symbol in 1.6 to 2.6 seconds. All
twenty-four probes returned the error page. The symbols are implausible on their
face: `S/PRST/2009/341` in a series running to about thirty a year,
`A/RES/64/299` when session 64 passed about 120, `A/RES/65/243 A` with a
trailing part letter the list invented.

So the symbol list carries entries that were never documents, and the API says
so in the one way it has. Filing that as a refusal cost three requests each and,
worse, fed the watcher a failure rate built from absences, which stopped a
perfectly healthy run.

A 403, 429 or 5xx is still a refusal. Of the 4,966 failures recorded so far,
4,714 are HTTP 503 from the hours when three fetches ran at once, and 251 are
the error page. Only the second kind was misfiled.

A redirect to anywhere else is still refused rather than guessed at. There is
one known meaning for one known destination, and nothing else is an answer.

## The symbol list still carried the old site's query strings

Found 2026-09-19 when the watcher warned at 5.1% for the first time in fourteen
hours. The refusals were all HTTP 400, on symbols like
`S/RES/1173 (1998)&Area=UNDOC` and `S/PV.6237amp;Lang=E`.

`all_docs_urls_uniq.txt` was collected from the old undocs.org, where the
document was addressed with a query string, and some of it survived HTML
escaping as a literal `amp;`. Normalising stripped the host and the language
prefix but left everything from the first ampersand onward. 170 of 39,409
symbols were affected, none of them yet settled.

Two things follow, and they are the same two as with the error page. Each bad
symbol cost three requests. And a 400 counted as a refusal, so 170 documents
that were never documents were on course to stop a healthy run.

A 400 or a 404 is deterministic: the request is malformed or names nothing, and
asking again changes nothing, so both are absences now. A 403, 429 or 5xx is the
server's state rather than ours and stays a refusal.

That is the third classification of this kind to get fixed: a 429 that was read
as absence, an error page that was read as a refusal, and now a client error
that was read as a refusal. The rule that survives all three is that the
question to ask of a response is not whether it succeeded but whether asking
again could change it.
